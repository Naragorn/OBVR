Feasibility study · OBVR

Oblivion Crash Suite

Catching, symbolicating and permanently fixing crashes in a 2006 x86 game binary — with tools that did not exist when the existing crash loggers were written.

Date 2026-08-30 Target Oblivion 1.2.0.416 Host xOBSE 22.13 plugin Status Study, no code written

Verdict

Feasible, and worth doing — but the value is not in the catching. Catching a crash and dumping registers has been solved for Oblivion since at least 2019, and xOBSE already writes a minidump on request. Everything hard sits downstream: turning an address into a function name, turning a stack into a call chain, turning one crash into a class of crashes, and turning that class into a patch you can prove fixed it.

Two measurements taken from your own Oblivion.exe decide the design. Only 3.7% of its functions keep a frame pointer, so the stack-walking method every existing Oblivion crash logger uses is structurally broken on this binary. And the executable still carries its original CodeView record, which means a synthetic PDB can be built that WinDbg and DbgHelp will load for it automatically — the door to the whole standard Windows debugging toolchain, TTD included, stands open.

Recommended shape: four layers, built in order, each useful on its own. Phase 1 is roughly a weekend and already beats every existing logger, because it stops guessing at the call stack and records what is actually knowable.

01

What already exists, and where it stops

Four bodies of prior art matter. None of them is a reason not to build; two of them are a reason to build differently.

xOBSE writes minidumps already

Measured xOBSE installs OBSEUnhandledExceptionFilter during initialisation when the installCrashdump setting is on, and calls CreateExceptionMiniDump to write OBSECrashDump.dmp into the game directory with thread info, unloaded modules, indirectly referenced memory and full memory info. [1] Your installation has the corresponding INI switch present and off: bCreateCrashDump=0 in Data\OBSE\obse.ini.

Derived The cheapest possible improvement to your crash situation costs one character. It is also not enough on its own: a minidump with no symbols for Oblivion.exe gives WinDbg an address and nothing else.

Cobb’s crash logger — the ancestor

Measured DavidJCobb/tes4-crash-logger is an OBSE plugin that calls SetUnhandledExceptionFilter and then patches the game’s import slot at 0x00A281B4 so the game cannot install its own filter over the top. [2] I verified that slot independently by parsing the import table of your Oblivion.exe: 0x00A281B4 is indeed KERNEL32!SetUnhandledExceptionFilter, and the game calls it from five sites. It logs a DbgHelp StackWalk trace, EIP, seven registers, 50 stack dwords and the loaded-module list.

Its stack walk is seeded with AddrFrame.Offset = Ebp. That is the load-bearing assumption, and section 03 shows it does not hold.

Yvile / WallSoGB — the state of the art in this family

Measured The New Vegas fork (same engine family, same 32-bit problem) adds what actually makes crash logs readable: it walks registers and stack looking for anything that looks like an object, reads its vtable, and resolves the RTTI type name, falling back to PDB symbols. [3] Its report is sectioned — exception, thread, calltrace, registry, stack, device, memory, playtime, game data, mods, modules, install. It hooks SetUnhandledExceptionFilter in kernel32 directly with a relative jump rather than through the IAT. Oblivion’s “Crash Logger Improved” descends from this line. [4]

Derived Two loggers that both redirect SetUnhandledExceptionFilter — one at the IAT, one at the export — will fight. Any suite built here must detect an already-installed handler and chain to it rather than assume it owns the process.

Buffout 4 / CrashLoggerSSE — the shape to aim at

Measured The Skyrim/Fallout 64-bit loggers are organised as Crash/Analysis, Crash/Introspection/HeapAnalysis, Crash/Modules/ModuleHandler, Crash/PDB/PdbHandler, Crash/ProblematicModules, Crash/ThreadDump. [5] PDB symbolication runs through msdia140.dll.

Derived That structure is the right decomposition and transfers. What does not transfer is the easy part underneath it: x64 binaries carry unwind tables in the PE, so a correct call stack is a library call. On x86 there is no such table — the Exception data directory in Oblivion.exe is empty.

Method and its uncertainty, for the 3.7% figure. I scanned .text for byte positions preceded by two 0xCC padding bytes — the compiler’s inter-function padding — and classified the bytes that follow. 32,261 such candidate entry points; 1,182 begin push ebp; mov ebp, esp. The candidate set is a heuristic and certainly contains some jump tables and data, so the denominator is soft. The conclusion is not: frame-pointer omission is the overwhelming default in this build, and no plausible correction to the denominator moves 3.7% anywhere near a usable majority.

Caveat on the heap figure. Six HeapAlloc call sites in a 6.4 MB binary means Oblivion is not allocating objects through the Win32 heap directly — it almost certainly draws large blocks and sub-allocates through its own manager, which is what Oblivion Stutter Remover replaces. Open I have not located or confirmed that allocator in the binary. Until it is found, IAT-level heap instrumentation gives you block-level pressure and OOM proximity, not per-object allocation tracking.

03

The hard problem: a call stack nobody can walk

A crash log is worth having because of the call chain. Everything else — registers, module list, the faulting address — tells you where the body fell, not who pushed it. And the call chain is exactly what this binary refuses to give up.

Three ways out, and what each really buys

Option A

Validated stack scan

Test every stack dword: does it point into .text, and do the bytes before it decode as a call? Cheap, no external data, degrades gracefully. Gives a noisy superset of the real chain, never a clean one.

Option B

Synthetic PDB with FPO data

Generate a PDB carrying the frame layout DbgHelp needs for FPO functions. Would give a genuinely correct walk and would fix WinDbg too, not just our logger. Also the only option with a real unknown in it — see section 05.

Option C

Record, don't reconstruct

Time Travel Debugging captures every instruction, so the call stack is a fact rather than an inference. Far too slow to leave on, unbeatable once you can reproduce. This is the repro tool, not the field tool.

Derived A and C are complementary and should both be built: A ships in every run, C is armed when you are hunting a specific bucket. B is the research bet that would make A obsolete and is worth one timeboxed experiment, not a dependency.

04

Proposed architecture

Four layers. Each is independently useful, each is testable, and none of them requires the next one to exist.

Layer 1 in detail: what a capture must not do

The existing loggers call calloc, SymInitialize and std::string inside the handler. If the crash was heap corruption — a large share of Oblivion’s crashes, by community consensus — the handler is now allocating on a broken heap while holding whatever lock the faulting thread held.

Derived The capture path must be preallocated at load time, allocation-free at crash time, and must write with raw WriteFile. OBVR already has exactly this: src/core/Log.cpp formats into a fixed 1024-byte stack buffer and writes with WriteFile, explicitly “so that the logger needs no heap”. And src/platform/ImportHook.cpp already replaces IAT entries by name. The infrastructure that makes a safe crash handler hard is already written and already used in this project.

Why VEH as well as the unhandled filter

An unhandled-exception filter, by definition, only sees exceptions nobody handled. A vectored handler installed as first-chance sees them all — including the ones the engine or another plugin swallows in a __try/__except. xOBSE’s own task manager catches exceptions around plugin tasks, [1] so those faults are invisible to every current logger.

Derived First-chance observation is where the new signal is. It must be sampled and rate-limited, not logged wholesale — C++ exceptions and probe faults are normal traffic — but a swallowed access violation that recurs every frame in a specific cell is precisely the kind of thing that later becomes a crash, and no existing tool for this game reports it.

05

Symbolication: the part that is genuinely new

An address like 0x0066BE6E is only useful to someone who has the binary open in a disassembler. Turning it into a name is what separates a crash log you can act on from one you can only forward.

The CodeView record is the key

Measured Oblivion.exe still carries an RSDS debug record: GUID 7bbd0a3a-8959-474f-aba3-082cd018c220, age 1. Derived Any PDB built with that exact signature will be accepted by DbgHelp, WinDbg and every symbol-server-aware tool as the symbols for this executable. Bethesda’s original PDB is not available, but its identity is, and identity is all the loader checks.

Measured wandel/pdbgen generates a PDB from a Ghidra database and explicitly relies on this: “If the CodeView entry in the DEBUG_DATA_DIRECTORY has been removed, it will fail to generate a pdb — this is because the path to pdb is dictated by the signature/guid and age values in this entry.” It currently generates global function symbols and data types, and states that function names should be resolved in the call stack. [6]

Where the names come from

Ghidra’s auto-analysis supplies roughly 32,000 function boundaries with generated names. Real names have to come from the modding community’s accumulated reverse engineering:

Measured The xOBSE source tree contains 1,574 distinct literal addresses in Oblivion’s address range across 293 source files, of which 266 are named constants — often with a signature in the comment, e.g. kGridCellArray_GetGridEntry = 0x00482150 and kLoadFile_CallAddr = 0x00748100 // __cdecl BSFile* LoadFile(char* path, ...). Derived That is a real seed corpus and it is machine-extractable, but it covers only single-digit percentages of the binary. Symbol coverage is a curve you climb over months, not a dataset you import once. The suite must therefore be designed to be useful at 5% coverage and better at 40%.

The open question worth one experiment

Open A PDB can carry FPO/frame-data streams describing how to unwind functions that keep no frame pointer, and DbgHelp historically consumed them for exactly this purpose on x86. I have not verified that current DbgHelp still honours them, nor that Ghidra’s per-function stack-depth analysis is accurate enough to generate them, nor that pdbgen can emit them — its README documents only function symbols and data types.

What would settle it: build a minimal PDB with a hand-written FPO record for one known FPO function, load it in WinDbg against a live Oblivion process, and check whether k unwinds past that frame. Half a day, and the answer decides whether Option B in section 03 is a project or a footnote.

06

Reproduction: what 2026 gives you that 2019 did not

A crash you cannot reproduce cannot be root-caused, only guessed at — and a guessed fix is the workaround this project does not accept. Three tools change the odds, all of them available on this machine and all of them 32-bit capable.

Time Travel Debugging

Measured TTD release 1.11.163 “adds support for recording x86 processes on x64 machines”. ARM32 recording was later removed; x86 was not. Recording can be restricted to specific modules with -module, which the release notes say can make recording substantially faster and traces smaller. A process can be launched under the monitor with -monitor, and since 1.11.304 there is a public in-process API to control the recorder from inside the recorded process, with -recordMode Manual to inject without recording anything until told. [7]

Derived This is the highest-value item in the whole study. The plugin can inject TTD in manual mode, keep recording off during normal play, and turn it on when the L0 instrumentation sees the precursor conditions of a known bucket — then the crash is captured with full instruction history and the call stack stops being an inference. Open I have not measured TTD’s slowdown on Oblivion, and a VR title has a hard frame budget; whether module-filtered recording is playable here is an empirical question, not a claim.

PageHeap and Application Verifier

Measured Full PageHeap places inaccessible guard pages at the ends of heap blocks and breaks into the debugger the instant a block is over- or under-run; it is enabled per-executable with gflags /p /enable Oblivion.exe /full and must be run under a debugger. [8]

Derived This converts the worst crash class — corruption that faults thousands of instructions later, somewhere innocent — into a fault at the exact instruction that wrote out of bounds. The caveat from section 02 applies: it guards Win32 heap blocks, and Oblivion sub-allocates. Expect it to catch corruption in plugin and library allocations reliably, and game-internal object overruns only when they cross a block boundary.

WER LocalDumps as the zero-code safety net

Measured Windows can be configured to write full user-mode dumps for a named executable with no debugger and no code, via HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\Oblivion.exe and DumpType=2. [9]

Derived Worth configuring today, before any of this is built. It catches the cases where our own in-process handler is itself the casualty — stack exhaustion, heap-corruption fast-fail, a fault inside the handler — which is exactly the set of crashes an in-process logger is worst at.

07

From a crash to a fix that stays fixed

The stated goal is not logs. It is permanent engine fixes. That imposes three requirements the existing loggers do not meet.

Bucketing, so a crash becomes a class

One crash is an anecdote. The unit of work is a bucket: a stable signature computed from the exception code plus the top few high-confidence frames, normalised to module-relative offsets. Every capture is filed under a bucket; a bucket accumulates occurrences, contexts and hypotheses. Derived With a scanned rather than walked stack, signature stability is the risk — noisy frames make unstable signatures. Mitigation: sign only on frames the scanner rated high-confidence, and treat the signature as versioned so it can be recomputed when the scanner improves.

The fix goes where the decision is made

The precedent is established and well-trodden: Measured EngineBugFixes, AveSithis Engine Fixes and BA_EngineFixes are all OBSE plugins that patch the engine binary in memory, and EngineBugFixes distinguishes “fixes” from “patches” and lets each be toggled separately. [10] xOBSE itself ships engine fixes in every release — null-parent-cell checks, iterator dereference fixes, container-loop corrections. [11]

OBVR already writes into Oblivion’s code segment through obvr::mem::SafeWrite, and already verifies expected bytes before patching with obvr::mem::Verify. A crash fix is the same operation as a camera hook, applied to a different address.

Every fix carries a test

This project’s standing rule is that decisions get extracted into pure functions over plain values and every flow through them is covered — the FrameLogic pattern, with tests/FrameLogicTest.cpp as the model. That applies here without modification, and it is what stops a fix from silently regressing:

  • The decision in a crash fix — is this pointer valid, is this index in range, should this call be skipped — is a pure function of plain values, and every branch of it is testable off-process.
  • The bucket signature function is pure and must be covered for the degenerate cases: no confident frames, one frame, frames outside any module, a recursive stack.
  • The stack scanner’s classifier is pure over a byte buffer and a module map, and every verdict it can return — confident, plausible, rejected — needs a case.

A fix without a test that fails before it and passes after it is a fix you will apply again in six months.

Effort and sequence

Estimates are for one developer already fluent in this codebase, and assume the suite lives beside OBVR rather than inside it — it must be usable with the VR mod off, or it cannot be used to debug the VR mod.

4–6 days

Buckets and context breadcrumbs

Signature computation and an on-disk bucket store. L0 instrumentation: heap block pressure via IAT counters, current cell and worldspace, frame counter, last N script or menu events into a ring buffer that the capture reads.

3–5 days

3–5 days, risk-bearing

Per-bucket binary patch behind its own toggle, a pure-function unit test for the decision it makes, and a recurrence check that reopens the bucket if the signature returns.

Derived Phases 0–2 are the minimum that beats the existing tools, and they total under two weeks. Phase 1 alone already produces better evidence than any current Oblivion crash logger, because it stops presenting an EBP walk as a call stack.

09

Risks, and what I could not verify

  • Open Whether DbgHelp still honours PDB FPO data on x86. Decides Option B. Settled by the half-day WinDbg experiment in section 05.
  • Open TTD’s runtime cost on Oblivion. Unmeasured. If module-filtered recording still costs 10×, armed recording is a bench tool only, not something usable during real play.
  • Open The game’s internal allocator. Not located in the binary. Its absence caps how much heap insight L0 can give and how much PageHeap can catch.
  • Open Whether Crash Logger Improved is already sufficient for your crashes. I read its lineage and its ancestors’ source, not its current binary. It may already do more than its ancestors; it cannot have solved the FPO problem, but it may extract enough object context to make many crashes obvious without any of this.
  • Derived Handler contention. Two crash loggers both redirecting SetUnhandledExceptionFilter, one at the IAT and one at the kernel32 export, is an unstudied interaction. If you keep an existing logger installed, chaining must be tested deliberately, not assumed.
  • Derived Attribution. With OBVR installed, OBVR is a defendant in every crash. The suite must record which patches were applied and be runnable with them disabled, or it will keep producing evidence that points at whichever DLL is nearest.
  • Derived Scope discipline. This can absorb unlimited time. The layered plan exists so it can be stopped after any phase with something working, rather than becoming a second project competing with the VR work.

10

Recommendation

Build it, in the order above, and start with the hour that costs nothing: enable the xOBSE dump, configure WER, install WinDbg. Then do Phase 1, because a capture that is honest about its own uncertainty is worth more than a walked stack that is confidently wrong — and because OBVR already contains the two pieces (heap-free logging, IAT hooking) that make it a short job.

Before Phase 2, spend the half day on the FPO experiment. It is the one unknown that changes the architecture rather than the schedule.
